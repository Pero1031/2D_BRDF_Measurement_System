# 実機のロボットアーム(DENSO RC8 + VP-6242)ドライバの設計メモ

P6 ③。`driver::IRobotArm` を、実機(RC8 コントローラに b-CAP でつなぐ)で実装するために調べたことと、その実装の記録です。
実機にはまだつないでいません。実機でないと分からないことは §7 にまとめてあります。

## 0. 調べたもの

| 資料 | 場所 | 分かったこと |
|---|---|---|
| 旧システムのアーム制御 | 旧プロジェクトの `source/Robot.cpp`、`header/RC8Params.h` | 旧システムが実機で使っていた b-CAP の呼び出し順、命令名、引数の型。§1 |
| b-CAP クライアントの SDK(ヘッダ、ソース、サンプル) | `<SDK>/Include/C`、`<SDK>/Src.Lib`、`<SDK>/Samples/C/bCapRobotMove`、`bCapSlaveMove` | 関数の仕様、エラーコード、`CurJnt` の使い方(サンプル)、ライセンス(MIT)、ライブラリは 32 ビット版だけだったこと |
| RC8 のプログラマーズマニュアル(DENSO の HTML 版。リポジトリの外に置いてある) | コマンドリファレンス: `ExtSpeed`(ページ 000196)、`CurJnt`(000177)、`TakeArm`(000151)、`GiveArm`(000144) | 外部速度は 0.1〜100 %。`CurJnt` はエンコーダで検出した全軸の現在角度。`TakeArm` の Keep の意味 |

## 1. 旧システムのやり方

`MoveArm` は、1 回動かすたびに、次を最初から最後まで繰り返していました(約 100 行の関数が、速度指定の有無だけ違って 2 つ)。

```
bCap_Open_Client("tcp:192.168.0.5", 5007, 0, &fd)       ← 右アーム。左アームは 192.168.0.2
bCap_ServiceStart
bCap_ControllerConnect("", "CaoProv.DENSO.VRC", "localhost", "")
bCap_ControllerGetRobot("Arm")
RobotExecute "Takearm"        (引数: 空の文字列)
RobotExecute "ExtSpeed"       (引数: double 1 個の配列。速度 [%] ← 速度指定ありの版だけ)
RobotExecute "Motor" "1"      (引数: 文字列)
bCap_RobotMove(補間 = 1, "J(j1,j2,j3,j4,j5,j6,-1)", "")
RobotExecute "Motor" "0"
RobotExecute "Givearm"
bCap_RobotRelease / ControllerDisconnect / ServiceStop / Close_Client
```

旧システムの問題(新しいものでは直す):

- **角度を整数に丸めていた**: `makeorder` が `(int)` でキャストしてから文字列にしていた。計算で求めた角度の小数部が、動作の前に失われる。
- **`bCap_Open_Client` の第 2 引数はタイムアウト**: 旧システムは、ここにポート番号 `SERVER_PORT_NUM`(5007)を渡していた。つまり、実際には「5007 ミリ秒のタイムアウト」として働いていた。ポートは、接続文字列 `"tcp:192.168.0.5"` にポートがないので、b-CAP の既定値(5007)になっていただけ。新しいものでは、`"tcp:<IP>:<ポート>"` と書いて、タイムアウトは別に指定する。
- **1 回ごとに接続・切断**: 1 台につき、1 回動かすたびに、ソケットを開いて制御権を取って返していた。
- **エラー処理がほぼない**: 移動の結果(HRESULT)を最後にまとめて返すだけで、途中の失敗のあとにモータを OFF にしたかどうかも、呼び出し側には分からなかった。
- 速度は `int`(1〜100 の %)。実際に使われていた値は 1、15、40 など。

## 2. 新しい流れ

`Rc8Arm` が、`IBcapApi`(b-CAP の薄い窓口)を使って、次の順に呼びます。

接続(`connect()`。**セッションにつき 1 回**):

| 順 | `IBcapApi` | b-CAP | 旧システム |
|---|---|---|---|
| 1 | `open("tcp:<IP>:<ポート>", タイムアウト, 再送 = 0)` | `bCap_Open_Client` | 同じ(ただしタイムアウトは別、ポートは文字列に) |
| 2 | `serviceStart` | `bCap_ServiceStart` | 同じ |
| 3 | `controllerConnect("CaoProv.DENSO.VRC", "localhost")` | `bCap_ControllerConnect` | 同じ |
| 4 | `getRobot("Arm")` | `bCap_ControllerGetRobot` | 同じ |
| 5 | `takeArm` | `"Takearm"`(引数なし) | 同じ(§4 の 2) |

移動(`moveJ(target, speed)`):

| 順 | 内容 | b-CAP |
|---|---|---|
| 0 | 速度、有限の数、可動域を、**送る前に**確かめる(§4 の 1) | — |
| 1 | `setExtSpeed(速度 × 100 [%])` | `"ExtSpeed"` |
| 2 | `setMotor(true)` | `"Motor"` `"1"` |
| 3 | `setTimeout(移動用)` → `moveJoint(J(...) の度)` → `setTimeout(通常)` | `bCap_SetTimeout`、`bCap_RobotMove`(補間 1) |
| 4 | `currentJoint` で、目標に着いたか確かめる(§4 の 3) | `"CurJnt"` |
| 5 | `setMotor(false)` | `"Motor"` `"0"` |

5 は、3 や 4 が失敗したときも必ず行う。

切断(`disconnect()`、デストラクタ): `Motor 0`(念のため)→ `Givearm` → ロボットの解放 → コントローラの切断 → サービス停止 → ソケットを閉じる。1 つ失敗しても残りを続ける。通信が途切れていたら、ソケットを閉じるだけにする。

そのほか:

- `currentJoints()`: `"CurJnt"` が返す 8 個(J1..J8)のうち、最初の 6 個を度からラジアンにする。
- `stop()`: `bCap_RobotHalt`。接続は保つ。
- `emergencyStop()`: `bCap_RobotHalt` → モータ OFF → 制御権を返して切断。以降は、再接続するまで動かせない。

角度は、ライブラリの内部では常にラジアンで、**度に変えるのは `Rc8Arm` の中だけ**です。`IBcapApi` は度(`Degrees6`)で受け渡します。

## 3. エラーの扱い

| エラー | 起きること | `Rc8Arm` の対応 |
|---|---|---|
| `InvalidArgument`(速度が範囲外、角度が NaN など) | コントローラに何も送らない | そのまま返す。接続は保つ |
| `JointLimit`(`[arm.limits]` の外) | 同上。メッセージに関節の番号と角度を書く | そのまま返す。接続は保つ |
| `DeviceError`(コントローラが断った。移動が目標に着かなかった) | 通信は生きている | モータを OFF にして返す。**接続は保つ**(次の移動ができる) |
| `Timeout`(`E_TIMEOUT`) | 移動の最中なら、動作中かもしれない。状態が分からない | 移動の最中なら、**通信が生きているうちに `Halt` → モータ OFF** を試みてから、ソケットを閉じる。再接続を求めるメッセージを付けて返す |
| `Communication`(`E_NOT_CONNECTED`、OS のソケットエラー `0x8091xxxx`) | 通信できない | 移動の最中なら、`Halt` とモータ OFF を 1 回ずつ試みる(届かなくてよい)。そのあとは、届かない命令を何度も待たないよう、ソケットを閉じるだけ。ほかの命令の最中なら、すぐにソケットを閉じる |
| 接続の途中の失敗 | 開いたものが一部だけある | 開いたものを逆順に閉じてから返す(通信が壊れていたら、ソケットだけ) |

`RealBcapApi` が、HRESULT を次のように分けます: `0x80000900` → `Timeout`、`0x80000902` と `0x8091xxxx` → `Communication`、それ以外(コントローラ自身のエラー)→ `DeviceError`。ソケットを開く段階(`bCap_Open_Client`)の失敗は、時間切れ以外は `Communication`。メッセージには、HRESULT の 16 進数と、分かる範囲の意味を付ける(例: `bCap_Open_Client failed: 0x8091274D (socket error 10061)`)。

TOPCON 側(`RealHsApi`)も、`HS_ERROR_PROCESS_TIMEOUT` を `Timeout`、装置が見つからない・つながらないエラーを `Communication` にそろえた。

## 4. 安全のための判断

実機のアームは、ぶつけると壊れ、人にも当たりうるので、旧システムになかった防御を入れてあります。

1. **送る前の可動域チェック**: `[arm.limits]`(既定は VP-6242 の出荷時のソフトウェアリミット)を外れる角度は、コントローラに送らず `JointLimit` で断る。コントローラ側のリミットとは別の防御。干渉(アーム同士のぶつかり)は、これまで通り `brdf check` と測定前のチェックが見る。
2. **`Takearm` は引数なし(旧システムと同じ)**: RC8 のマニュアルでは、`Keep = 0`(省略時)なら、制御権を取った時点で、内部の速度・加速度・減速度を 100 に、ツールとワークの座標系を 0 に初期化する。実効の速度が、前に動かしたプログラムの設定に左右されず、`ExtSpeed` だけで決まる。DENSO のサンプルは `Keep = 1` にしているが、旧システムが実機で使っていたのは引数なし。
3. **着いたかの確認**: 移動のあと `CurJnt` を読み、目標との差が `arrival_tolerance_deg`(既定 1°)を超えたら `DeviceError`。命令が無視されたときなどを見つける。目標より緩い値にしてあるのは、実機での差が分かっていないため(§7)。
4. **モータは移動の間だけ ON**: 旧システムと同じ。移動のあとはブレーキがかかった状態になる。
5. **再送は 0**: 通信の再送を有効にすると、時間切れのあとに移動の命令がもう一度届くおそれがある。
6. **待ち時間を 2 種類に分ける**: 通常の命令は 5 秒、移動は 3 分(`[controllers]` で変えられる)。遅い速度で遠くへ動かすと、旧システムの 5 秒では足りないはず。移動の待ち時間は、移動のあとで必ず元に戻す。
7. **別スレッドからの停止はできない**: b-CAP は 1 本のソケットを使うので、`moveJ` の最中に別のスレッドから `stop()` を呼べない。動作中の非常時には、ティーチングペンダントの非常停止を使う。

## 5. ビルド

b-CAP のクライアント SDK は、DENSO が **MIT ライセンス**で配布していますが、付属の `bCAPClient*.lib` は **32 ビット版だけ**で、このプロジェクト(64 ビット)ではリンクできません。そこで、SDK のソースを、64 ビットの静的ライブラリ(`bcap_client`)としてビルドします。

```
cmake --preset default -DBRDF_WITH_BCAP=ON -DBCAP_SDK_DIR=<...>/CapLib/DENSO/RC8
```

`BCAP_SDK_DIR` は、`Include/C/bCAPClient/bcap_client.h` と `Src.Lib/*.c` を含むフォルダ。オプションを付けなければ(既定)、アームのドライバの実機用の部分(`RealBcapApi`)はビルドされず、ほかのすべては今まで通りビルドしてテストできる。実行時に必要な DLL はない。

SDK のソースをそのまま使うために、次のことをしている(`CMakeLists.txt`)。

- SDK 同梱の古い `stdint.h` は、今の MSVC のものと型の定義がぶつかる。ヘッダをビルドフォルダにコピーするとき、この `stdint.h` だけコピーしない(ソースの `#include "stdint.h"` は、MSVC 標準のものになる)。SDK のファイルは、リポジトリには入れない(ビルドフォルダにコピーするだけで、書き換えもしない)。
- SDK のソースは 32 ビット時代のもので、ポインタを `int` に切り詰める警告が出る。切り詰めているのは、同じバッファ内の 2 つのポインタの差(数 KB)とソケット番号(小さい整数)、それに使わないシリアル通信の部分だけなので、実害はないと判断して、このライブラリだけ警告を消している。
- `RealBcapApi.cpp` は `<windows.h>` を include しない(ライブラリが、独自の `VARIANT`、`BSTR`、`SysAllocString` などを持っているため)。

ビルドして確かめたこと(2026-11): `-DBRDF_WITH_BCAP=ON` と `-DBRDF_WITH_TOPCON=ON` を両方付けて、64 ビットの Debug がビルドでき、全テストが通る。

## 6. テスト

`tests/test_rc8_arm.cpp`。

- **フェイクの `IBcapApi`**: 呼ばれた順を記録し、指定した呼び出し(の何回目)で、指定したエラーで失敗させる。失敗のあと通信が死んだままにもできる。ソケット、サービス、コントローラ、ロボット、制御権の開閉と、モータの状態、速度、待ち時間、移動の目標を数える。ロボットは、移動の命令どおりの位置に動き、命令を無視したり、少しずれて着いたりもさせられる。
- 確かめていること: 接続の順序と引数、接続が 1 回だけであること、切断の逆順、どの段階で失敗しても開いたものが閉じること、移動の手順(モータの ON/OFF、待ち時間の切り替え、小数の角度、速度の変換)、送る前の拒否(未接続、速度、NaN、可動域)、どの命令が失敗してもモータが OFF に戻ること、着かなかった移動、時間切れと通信エラーのときの後始末の順序(止める → モータ OFF → ソケットを閉じる)、停止・非常停止、2 台の独立。
- テストが、**実際の不具合を見つけた**: 通信が途切れたあとの後始末で、「モータ OFF」が届かなかったのに続けて「制御権を返す」を送ろうとしていた。直した。
- `-DBRDF_WITH_BCAP=ON` のビルドでだけ走るテスト: 実際のライブラリで、誰も待っていないポートへの接続が、`Communication`(ソケットエラー 10061)ですぐ失敗し、何も開いたままにならないこと。ASCII でない名前を送る前に断ること。
- 設定の読み書きとエラー(`[controllers]`)、設定からの `Rc8ArmConfig` の組み立て。

## 7. 未確認の点(実機で確かめる)

| # | 内容 | 確かめ方 |
|---|---|---|
| 1 | `J(...)` の 7 番目の `-1` の意味と、小数の角度を受け付けること(旧システムは整数だけ送っていた) | 実機で、小数の角度を低速で 1 回動かす |
| 2 | 1 回の接続の中で、`Takearm`、`ExtSpeed`、`Motor` を何度も繰り返しても問題ないこと(旧システムは、1 回の移動ごとに接続していた) | 同じ接続で、続けて何回か動かす |
| 3 | `bCap_RobotMove` が、動作の完了まで戻ること。`bCap_SetTimeout` で変えた待ち時間が、その移動の待ちに効くこと | 長い距離を遅い速度で動かして、戻るまでの時間を測る |
| 4 | `CurJnt` が度で、8 個(最初の 6 個が J1..J6)返ること。移動後の実際の差(`arrival_tolerance_deg` の既定値 1° が適切か) | 数回動かして、目標との差を記録する |
| 5 | 通信が途切れてソケットだけ閉じたとき、コントローラが制御権とハンドルを解放すること | 故意にケーブルを抜く、または強制終了のあとに、再接続できるか |
| 6 | `bCap_RobotHalt` が、動作中に効くこと。別スレッド(別の接続)からの停止は、今は未対応 | 実機で、低速の移動の途中に別の接続から止められるか(必要なら、停止用の接続を設計に足す) |
| 7 | `Takearm` が通る、ティーチングペンダントのモード(自動、マニュアル、など) | 実機で。通らないときは、メッセージにペンダントのモードを疑うよう書いてある |
| 8 | `Motor` ON にかかる時間。2 台 × 13 姿勢の測定の時間への影響 | 時間を測る。長いなら、「移動の間だけ ON」の方針を見直す |
| 9 | 実機のコントローラの IP アドレスとポート(旧システムの値 192.168.0.2 / 192.168.0.5 / 5007 を既定値にしている) | ネットワーク設定を確認する |
| 10 | 左右のアームと、実機の RJ / LJ の対応 | 低速で 1 台ずつ動かして、どちらが光源側かを目で確かめる |
| 11 | 実効の速度(内部速度 100 × 外部速度)。旧システムの 1%、15%、40% と同じ値で、同じ速さになること | 同じ値で動かして、旧システムとの速さを見比べる |
